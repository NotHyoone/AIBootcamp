# 오늘의 모먼트 · 후속 문서 작성 계획

기준일: 2026-11-04. 대상은 Diary Simple v3의 UI 개선과 팀 인수인계입니다. 현재 구현을 설명하는 문서와 향후 제안을 구분하며, 미연결 기능을 구현된 것으로 기술하지 않습니다.

## 1. 이번 작성 범위

- [DESIGN_STYLE.md](DESIGN_STYLE.md): 현재 디자인·10개 팔레트·반응형·상태 표현 및 별도의 개선 제안.
- 이 문서: 후속 문서의 목차·근거·작성 순서·완료 기준.
- [프로젝트 README](../README.md): 위 문서의 진입 링크만 추가.

후속 4개 문서는 디자인 초기 세팅에서 생성했습니다. 현재 작업 진입점은 [디자인 안내](design/README.md), 실행 상태는 [ROADMAP](ROADMAP.md), 검증 결과는 [QA](QA.md)입니다. 아래는 문서 역할과 작성 기준으로 유지합니다. 초기 문서 작성 이후 디자인 원본·빌드·HTML도 갱신했으며 과거 증거는 유지했습니다.

## 2. 작성 순서와 산출물

파일 위치는 모두 이 `docs/` 폴더입니다. 아래 파일은 현재 생성되어 있습니다. 상세 내용은 각 문서에서 관리합니다.

| 순서 | 파일 | 역할 | 선행 조건 |
|---|---|---|---|
| 1 | `UI_SPEC.md` | 화면·상태·전환·문구의 기준 | 디자인 가이드와 현재 앱 확인 |
| 2 | `ARCHITECTURE.md` | 구현 구조와 변경 위치 안내 | 화면·상태 용어 확정 |
| 3 | `ROADMAP.md` | 개선 항목의 실행 가능한 작업 목록 | 화면 명세와 구조 설명 완료 |
| 4 | `QA.md` | 개선 작업의 합격 기준과 결과 기록 | 작업별 완료 조건 정리 |

### 2.1 UI_SPEC.md — 화면·상태 명세

**목차:** 서비스 경계 → 화면 목록 → 사용자 흐름 → 상태·문구 표 → 모바일 차이 → 예외·복구 → 미확정 항목.

- [manifest](wireframes/manifest.json)의 WF-01~14, ST-01~12를 재사용합니다. 새 ID를 중복 부여하지 않습니다.
- 각 화면에 목적, 진입 경로, 입력·표시 데이터, 사용자 동작, 다음 화면·복귀 위치, 빈 상태·오류를 기록합니다.
- 실제/예시 모드, 기록 없음/분석 없음, 대기/실패/빈 카드, 기록 수정에 따른 분석 무효화를 구분합니다.
- 기록·카드 전환, 통계 3종, 날짜 필터, 도감→연결 기록→상세의 복귀 흐름을 다룹니다.

**근거:** [와이어프레임 설명](wireframes/README.md), [app.js](../scripts/app.js), [통계 뷰](../scripts/statistics-view.js), [도감 뷰](../scripts/catalog-view.js).

**완료 기준:** 26개 화면·상태 ID를 빠짐없이 대응시키고, 와이어프레임과 코드의 차이는 차이 표에 명시합니다. 예시·향후 기능을 실제 기능으로 기술하지 않습니다.

### 2.2 ARCHITECTURE.md — 구조·개발 인수인계

**목차:** 실행·빌드 → 모듈 책임 → 상태와 데이터 흐름 → 테마·출력 → 변경 절차 → 외부 연동 경계.

- `core`·`diary-core`·`cards`·`statistics`의 도메인 처리와 화면 모듈의 책임을 구분합니다.
- 기록 ID·버전·분석 상태가 카드·통계·도감으로 전달되는 흐름을 설명합니다.
- 메모리 기록, 예시 데이터, localStorage의 디자인 설정을 나눠 설명합니다.
- 템플릿과 모듈을 단일 HTML로 묶는 빌드 순서, `base.css`의 글꼴만 추출하는 동작, 라이선스 내장을 설명합니다.
- 백엔드 분석은 미연결입니다. 프런트 7유형과 루트 모델 6분류의 차이를 연동 제약으로 기록하며 임의 변환 규칙을 만들지 않습니다.

**근거:** [빌드](../tools/build.mjs), [셸](../templates/shell.html), [README](../README.md), `scripts/`의 실제 의존 관계.

**완료 기준:** 새 담당자가 소스 수정→HTML 재생성→관련 검증 위치를 찾을 수 있고, 저장·분석 기능의 현재 한계를 이해할 수 있어야 합니다. 신규 API나 스키마는 설계하지 않습니다.

### 2.3 ROADMAP.md — UI 개선 작업 목록

**목차:** 우선순위 기준 → 작업 표 → 의존 순서 → 검토·승인 지점 → 보류 항목.

작업 표에는 ID, 문제와 근거, 기대 동작, 우선순위, 관련 모듈, 선행 작업, 완료 조건, 검증 방법, 상태를 둡니다. P1은 사용·접근성 점검, P2는 일관성·자산 개선으로 시작합니다. 담당자와 일정은 미정으로 표시하고 임의로 배정하지 않습니다.

초기 후보는 작은 화면의 조작 영역, 초점·키보드 흐름, 차트 글꼴, 캐릭터 자산, 최신 캡처·검증 자료 정리입니다. 각 항목은 재현·영향 확인 후 구현 작업으로 전환합니다. 계정·API·서버 저장은 별도의 향후 범위로 표시합니다.

**완료 기준:** 모든 작업에 관찰 가능한 완료 조건과 검증 절차가 있고, 디자인 승인이나 자산 준비가 필요한 의존성을 식별합니다. 근거가 없는 항목은 확정 결함 대신 조사 과제로 표기합니다.

### 2.4 QA.md — 검증·인수 기준

**목차:** 환경 준비 → 자동 검사 → 수동 검사 → 기능·테마·화면 크기 표 → 결과 기록 → 알려진 한계.

- 기록 작성·수정·삭제, 모드 분리, 통계 누락값, 도감 재계산, 카드 PNG를 검증 대상으로 삼습니다.
- 임계값 30%·60%·90% 전후, 동률, 버전 불일치, 분석 실패·누락을 기존 단위 테스트와 연결합니다.
- 5개 테마 × Light/Dark, 시스템 모드 변경, 설정 유지·잘못된 값·저장소 차단을 확인합니다.
- 크기는 1366×768, 1440×900, 390×844, 360×640, 320×568을 사용합니다. 넘침·가림·내부 스크롤을 확인합니다.
- 키보드·초점·한국어 스크린리더 안내, 200% 확대, 모션 감소, 실기기 키보드, Safari/Firefox를 수동 항목으로 둡니다.
- PNG는 1080×1620, 테마 반영, 원문 미포함을 확인하며 캡처에는 합성 예시만 사용합니다.

**완료 기준:** 결과에 실행일, 브라우저·버전, 명령·환경, 통과/실패/미실행, 증거 위치를 남길 양식이 있습니다. 미실행 항목과 과거 결과를 최신 통과로 표시하지 않습니다.

## 3. 문서 작성·검토 절차

1. 작성 시점의 소스와 변경 상태를 확인하고 문서 기준일을 기록합니다.
2. 코드의 현재 동작을 먼저 기술하고, 개선 제안·미검증·미확정을 별도 표기합니다.
3. 상대 링크로 소스와 기존 와이어프레임을 연결합니다. 후속 파일은 실제 생성된 뒤 README에 링크합니다.
4. 소스값, 화면 ID, 문서 내부 링크를 검사하고 문서 변경 범위를 확인합니다.
5. UI 구현을 변경하는 후속 작업에서는 HTML을 재생성하고 관련 테스트를 실행한 뒤 문서와 증거를 갱신합니다.

기존 `previews/` 이미지와 `browser-results.json`에는 이전 UI 정보가 있으므로 현재 화면의 검증 근거로 재사용하지 않습니다. 기존 자료를 삭제하거나 덮어쓰지 않고, 새 증거를 만들 때 촬영일·대상 화면·테마·모드를 식별합니다.

## 4. 검증 명령과 실행 조건

메인 프론트 폴더 `frontend`에서 실행합니다.

```powershell
# UI 소스를 바꾼 경우에만 HTML 재생성
node tools/build.mjs

# 도메인 회귀 검사
node --test tests/*.test.cjs

# 브라우저·테마·기존 와이어프레임 검사
node tests/browser.cjs
node tests/themes.cjs
node tests/wireframes.cjs
```

브라우저 검사는 Node에서 로드할 수 있는 Playwright와 Chrome이 필요합니다. 기본 경로가 없으면 `CARDEX_PLAYWRIGHT`에 Playwright 모듈 경로, `CARDEX_CHROMIUM`에 브라우저 실행 파일 경로를 지정합니다. 와이어프레임 생성기를 수정한 경우에만 `node tools/build-wireframes.mjs`로 해당 산출물을 재생성합니다.

문서만 변경할 때는 링크·수치·참조 일치 여부를 검사합니다. 위 명령이 기재되어 있다는 사실은 테스트 실행을 의미하지 않습니다. 브라우저 검사는 전체 접근성·실기기 호환성을 대신하지 않습니다.
